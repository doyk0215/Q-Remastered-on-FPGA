# Delivery Requirements

Derived from the PRD/addendum and its recorded EE2026 manual context (printed pages 10–15). These obligations belong to project release rather than additional runtime modules.

## Board demonstration

- Show the integrated core game, visible stroke rotation, state feedback and retry/navigation in the typical 2–5 minute team demonstration.
- Demonstrate only capabilities present in the delivered single bitstream. Record achieved responsiveness/update rates before reporting them.
- Retain the recorded course-staff mouse-only exception; the manual's default switch requirement is not silently treated as satisfied by unused switches. Basys3, OLED and LED roles remain included; optional devices earn no marks by themselves.
- Evaluation concerns functionality, robustness/reliability, UI and UX. Choose scope that supports a reliable demonstration.

## Submission

- Include one successfully generated, board-tested bitstream in the final archive.
- Keep the archive at or below 500 MB unless prior approval permits otherwise.
- Download/unzip and verify the submitted archive, including the required usable bitstream and files.
- Retain reproducible source, project/build settings, constraints, memory initialization and source provenance/notices. Reused HDL in other languages remains permitted by the project decision.
- Report only integrated, demonstrable capabilities. Follow the four-page report structure, applicable team-size word limits and required colour/layout rules.
- Include required references/documentation for open-source sources and AI/code-generator use, and complete peer feedback.

## Items requiring the current course instructions

Exact team word limits, colour-layout details, submission naming/deadlines and peer-feedback mechanics are not specified numerically in the current authored inputs. The release coordinator must retrieve/confirm them from the course manual/portal before submission; this spec does not invent them.
